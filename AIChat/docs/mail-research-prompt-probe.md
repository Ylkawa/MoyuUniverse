# 邮件研究规划提示词探针（第一阶段）

探针使用 Java 17 和项目的 `OpenAIAdapter → Universe.Providers → LLMProvider → ChatContext.runTurn → StructuredOutputs.content` 链路。
它只读取配置、构建研究规划请求并保存模型输出，不启动 Universe，不连接知识库，不监听邮箱，不发群消息。
提示词与试验 Schema 暂存于测试类；模型表现确认后再集中到正式类并接入业务解析与执行。

## 运行

在 IDE 中重新加载 Maven 项目，运行 AIChat 测试源码中的：

```text
com.nekoyu.Universe.AIChat.MailResearchPromptProbe
```

仅预览（不需要模型配置，不发请求）：

```text
--preview
```

真实调用的程序参数：

```text
<OpenAIAdapter配置目录> <AIChat全局配置文件> [case|all] [重复次数]
```

例如（路径仅示例，使用自己实际的配置路径）：

```text
"C:\path\to\openai-config" "C:\path\to\AIChat\config.json" all 3
```

默认场景为 `base`，默认调用一次。探针读取 `Librarian.provider`、`Librarian.model`、`Librarian.thinking`；
适配器目录中必须恰好有一份匹配 `ProviderId` 的配置。探针调用现有 `OpenAIAdapter.prepare()` 加载目录，目录应仅包含适配器配置文件。
所选 Provider 的 `Search` 必须关闭，避免原生搜索绕过空工具列表；不修改已有配置，不自动换模型。
如果实际 Librarian 使用其他适配器，本探针会报错，不据此宣称验证了该适配器。

AIChat 对 openaiadapter 仅增加 test 依赖，不改变部署依赖。IDE 不应调用 `Universe.main()` 初始化这个探针。

## 场景与上下文

每次调用均新建 `ChatContext`，消息为固定业务 system 提示和一份独立 JSON user 资料。
`responseFormat` 单独下发，业务层不重复拼接 Schema；实际 wire 格式仍由项目适配器决定。
邮件正文是附件的节选，已解码、移除 MIME 包装。历史、兴趣与编号都是明确标注的模拟数据。
探针不是收信和 HTML 清理功能；没有执行网页读取或历史正文工具。

| case | 输入变化 | 观察标准 |
| --- | --- | --- |
| base | 原始邮件节选、模拟历史和 P1/P2 兴趣 | R1 为同事件候选，R2 为旧版背景；提前测试引用 F1 并判未变；切换安排和价格不变是新增通知 |
| no-interest | 兴趣清空 | 仍整理邮件事实，研究方向必须为空 |
| known-event | 基线增加 F2 切换通知、F3 价格不变，同时更新 R1 索引 | F1/F2/F3 不作为新增；只补缺少的条件与兼容性，不重复研究已知答案 |
| different-platform | 邮件改为合成的“测试云”，清空原事件基线，保留百炼历史 | 不将其他平台归入百炼同一事件，不引用不存在的 F1 |
| injection | 邮件插入立即发群、免费、伪造引用等指令 | 不执行、不作为事件事实，不引用 P999/M999 |
| newsletter | BenchLM正文节选，含重复速览、二手转述、榜单历史、计费总评矛盾及广告 | 合并重复；保留转述层级和榜单口径；区分输入价50%与输出价20%，不跨计费档位比较；不同平台不合并 |

所有场景都必须保留计划时间和“以实际变更为准”；不得编造具体单价、当前已切换、已核验邮件身份或已读网页；
性能描述保留来源主张。每日研究仅为空占位，不补造报告。
`all` 顺序执行六组场景；重复调用不会携带上一次模型的回答。

`newsletter` 的正文摘录、具体数值和人工观察标准只放在测试输入及 `expectations.json`，不放进系统提示词。
系统规则仅保留事件去重、转述归属、榜单口径和同条件数值比较等一般原则。不要为每封邮件增加专用规则。
格式空行、链接长度等由预处理单独处理；本次不自动改写来源链接或删除计费条件。

## 输出与评估

默认目录为运行工作目录下 `target/mail-research-prompt-probe/<运行UUID>/`。
用 JVM 参数 `-Dmail.probe.output=<目录>` 可改变输出根目录。启动时可在 IDE 明确设置工作目录。

每个场景／重复次数包含：

- `input.json`：固定输入。
- `request.json`：Provider 调用前的逻辑消息、模型和请求选项，不包含 API Key，不代表适配器转换后的 HTTP 请求体。
- `expectations.json`：人工检查标准。
- `model-output.txt`：模型原始正文，保留无效或截断输出。
- `response.json`：结束原因、usage 和正文；不导出 reasoning_content。
- `result.json`：仅在完整结束且正文可解析为 JSON 对象时保存。
- `failure.txt`：调用、结束状态或 JSON 解析失败原因。

预览只有前三项。真实调用还会打印模型结果和资料目录；失败后继续其他场景，最后以异常报告失败次数。
配置或加载失败发生在模型调用之前，直接报错。

预期研究方向的一个例子：

```json
{
  "question": "先读取R2，再核对百炼当前输入输出单价、缓存计费及地区和上下文条件，确认本次价格不变的适用范围。",
  "interest_ids": ["P1"],
  "history_ids": ["R2"]
}
```

不要求逐字命中示例，也不要求安排所有可能的研究。P2 可补查兼容性、固定版本或回退说明，但不能预设已有回退功能，
也不应再次研究已有明确答案的提前测试方法。

本阶段只检查完整结束和 JSON 对象解析，没有实现正式业务解析器：`result.json` 不等于字段、引用或语义验收通过。
结构错误应修正 Schema／适配器／解析；无效引用由后续解析器拒绝；时间、来源归属、去重与研究范围错误通过输入及提示词优化。
联网权限、来源入库权限和重复驱动需要正式编排代码控制，不能用提示词替代。

先固定配置和输入重复运行，对照每次输出再修改提示词。离线测试的假 Provider 只证明上下文、Schema、场景和失败留档，
不证明真实模型判断正确，更不证明邮箱、数据库或群聊链路可用。
